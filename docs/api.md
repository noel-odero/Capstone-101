# Architecture and API

## Boundaries

React calls the .NET API through Vite's `/api` proxy during development. The API validates and authenticates requests, calls the internal Python service, checks returned contracts and persists completed runs in PostgreSQL. Python loads the frozen policies from local files, runs the shared scientific environment and stores no user data. No external model host is needed.

| .NET project | Responsibility |
| --- | --- |
| `Amr.Domain` | Enums and value types |
| `Amr.Application` | DTOs, application services, mappings, metric catalogue and interfaces |
| `Amr.Infrastructure` | Python HTTP client, EF Core persistence, migrations and dependency probes |
| `Amr.Api` | Controllers, authentication, rate limiting and problem responses |

The frontend is organized by feature; `history` contains History and Insights, `model-explorer` contains state-space/evidence exploration, and `simulation` retains the analysis-configuration and original 3D evaluation routes. The existing `/app/profile`, `/app/simulation` and recommendation URLs remain compatible despite updated public labels.

## Public routes

All paths below are relative to `/api/v1`. Routes require authentication except session, registration, sign-in, health, model metadata and the antibiotic catalogue. Cookie sessions use email/password sign-in; there is no Google OAuth integration. Retrieve the session's antiforgery token and send it in `X-CSRF-TOKEN` for POST requests, including authentication POSTs.

| Route | Behavior |
| --- | --- |
| `GET /auth/session` | Authentication state, current user and CSRF token |
| `POST /auth/register`, `/auth/sign-in`, `/auth/sign-out` | Account/session management |
| `GET /health`, `/health/live` | Dependency readiness / process liveness |
| `GET /model`, `/antibiotics` | Verified model metadata / canonical action catalogue |
| `POST /profiles/validate` | Profile eligibility and candidate transition evidence, including valid terminal states |
| `POST /simulations` | Execute and save one `ppo`, `dqn` or `random_susceptible_baseline` episode |
| `POST /comparisons` | Execute and save all three strategies under shared conditions |
| `GET /simulations/{id}`, `/comparisons/{id}` | Retrieve a stored run of the matching kind |
| `GET /recommendations/{simulationId}` | Policy-selected steps from a saved learned-policy run |
| `GET /simulations/recent` | Paginated archive of simulations and comparisons, newest first |
| `GET /samples`, `/samples/{id}` | Account-owned labeled profiles, creation dates and linked evaluations |
| `POST /samples` | Save a labeled profile without executing a policy |
| `GET /analyses` | Filtered saved evidence for Analysis Insights |
| `POST /analyses/compare` | Inspect 2–50 distinct saved analysis UUIDs without rerunning them |
| `GET /analysis-collections`, `POST /analysis-collections` | List/save account-owned research collections |

`POST /comparisons` optionally accepts `sampleId`. Ownership and the sample's original profile are checked before execution; the run and link commit together. Samples track pending/analyzed inputs. History archives work already done. Insights compares recorded evidence; Model Explorer is a read-only view of model states and evidence coverage. They do not duplicate sample storage.

`GET /analyses` accepts `page`, `pageSize`, seven-bit `profile`, `initialResistantCount` (0–7), `strategy` (`ppo`, `dqn`, `baseline`, `missing_dqn`), inclusive UTC `from`/`to` timestamps and `sort` (`newest`, `oldest`, `ppo`, `dqn`, `baseline`, `disagreement`). Burden sorts ascend with missing policies last; disagreement orders absolute PPO–DQN burden differences descending. `POST /analyses/compare` takes `{ "analysisIds": ["uuid", "uuid"] }` and preserves selection order.

Missing and foreign-owned resources return the same 404. Missing policy results stay absent/null, never zero. Comparison compatibility checks cover model/data identities, scenario, horizon, action order/mask, reward, metric definitions, service versions, profiles and RNG seeds. Repeated random draws are flagged. No pooled significance test or automatic algorithm winner is inferred. Collections save a name (80 characters), optional question (500 characters) and 2–50 ordered analysis UUIDs. Browser exports contain validated stored evidence.

## Persistence and errors

Run IDs are UUIDs generated by Python per execution; the same UUID addresses the stored resource. Sample and collection IDs are separate server-generated GUIDs. They do not encode the resistance profile or RNG seed.

Creation returns `201 Created`, `Location` and `isPersisted: true` only after the transaction commits. Only complete, contract-valid results are saved. A failed write produces an error, not a success containing an uncommitted ID. Python is called once per request; there is no automatic POST retry or idempotency key. A deliberate client retry creates a new evaluation. A disconnect racing a commit can leave a stored run whose response was not received.

| Table | Stored information |
| --- | --- |
| `users` | Accounts and password hashes |
| `samples` | Owned labels, profiles and creation dates |
| `model_versions` | Fingerprinted model/simulator identities and configuration |
| `experiment_runs` | Completed run inputs, ownership, seeds, timestamps and contract |
| `strategy_runs` | Strategy identity, copied metrics and state snapshots |
| `step_traces` | Ordered actions, candidate outcomes, source IDs and sampled transitions |
| `analysis_collections` | Owned questions and ordered references to saved analyses |

The run, strategies and traces save together. Model-version upserts are race-safe. Deleting a run cascades through its strategies and traces; referenced model versions are protected. JSONB object key order is not significant. Retrieved values are recorded outputs, not recalculated results. All EF migrations and the model snapshot are required for fresh and existing databases; schema updates are explicit, never applied automatically at startup.

Public failures use `application/problem+json` with stable `code` and `correlationId`; `X-Correlation-ID` supports tracing. Validation is 422, missing resources 404, unavailable database/model/service 503, invalid upstream responses 502, and persistence/contract/internal errors 500. Authentication and CSRF failures retain their corresponding HTTP status. Database unavailability is never disguised as an empty list or missing resource. `/health` returns 503 with a report when dependencies or migrations are unready; `/health/live` does not touch them.

Use the same-origin proxy locally. Production hosting requires explicit HTTPS/proxy, host and secret configuration. Current controller DTOs and request/response fixtures are the executable JSON contract; the public API does not generate OpenAPI clients.

## Python service

Use one Uvicorn worker. Startup validates both checkpoint hashes, data identities and manifest contracts before becoming ready. Predictions are serialized inside the engine. A validation failure leaves `/internal/health` unready and model-dependent requests return 503. Interactive internal API documentation is available at `http://127.0.0.1:8000/docs` while running.

Internal routes are `GET /internal/health`, `/model`, `/antibiotics` and `POST /internal/profiles/validate`, `/recommend`, `/simulate`, `/compare`. Internal requests/responses use snake_case; the public API maps them to camelCase. Horizon eight and `REF_UNIFORM_SUPPORTED` come from the verified manifest, not request overrides. Unknown fields are rejected. Optional environment/policy seeds are recorded; deterministic learned policies ignore policy RNG seeds, while the baseline uses them.

`states` has one more entry than `steps`; step i moves state i to i+1. An unsupported step records empty candidates, a null selected outcome and an unchanged profile. The comparison checks shared conditions and equal per-step transition seeds, but explicitly does not guarantee identical outcomes after different actions. Internal errors use `{ "error": { "code", "message", "request_id" } }` and `X-Request-ID`; paths and traces stay in server logs.

## Verification and fixture maintenance

From PowerShell at the repository root, with PostgreSQL running:

```powershell
$env:AMR_TEST_POSTGRES = [Environment]::GetEnvironmentVariable('AMR_TEST_POSTGRES', 'User')
$env:AMR_REQUIRE_POSTGRES = 'true'
dotnet restore backend\Amr.sln --locked-mode
dotnet build backend\Amr.sln --no-restore -warnaserror
dotnet test backend\Amr.sln --no-build --filter 'FullyQualifiedName!~LivePythonServiceTests&FullyQualifiedName!~LiveEndToEndTests'
.\backend\scripts\run-live-tests.ps1
```

Each database test class creates and drops its own `amr_it_<guid>` database, requiring an admin connection on a local/disposable PostgreSQL instance. Without the require flag or connection, database tests can skip. The live script starts an isolated Python service and requires both live and database tests to execute.

Python tests live with `simulation`, `ml`, `service` and `experiments`; frontend feature tests cover navigation, schema handling and user workflows. GitHub Actions runs Python, .NET and live-service checks. Regenerate backend Python-response fixtures with `.\.venv\Scripts\python.exe -B backend/tests/Shared/Fixtures/generate_python_fixtures.py`. Frontend public-API captures live in `frontend/src/test/fixtures/captured`; capture updated responses from the running API when its contract changes. Review fixture changes alongside their schema and tests.
