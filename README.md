# AMR Decision Support

### Exploring reinforcement learning for antibiotic sequencing under simulated antimicrobial resistance

Antimicrobial resistance (AMR) makes antibiotic selection a problem that extends beyond the immediate treatment outcome. The sequence in which antibiotics are selected can influence how resistance evolves and which treatment options remain susceptible over time.

**AMR Decision Support** is a research prototype that investigates this sequential decision-making problem using reinforcement learning and a simulated *E. coli* resistance environment.

The project implements a frozen Proximal Policy Optimization (PPO) policy and compares its simulated behavior with a random susceptible-action baseline. A planned interactive dashboard will let users inspect starting resistance profiles, follow simulated resistance trajectories, compare policy outcomes, and examine the actions selected by the model alongside the environment's transition-support information. The simulation, the PPO inference service and the public API already exist; the dashboard is not yet built.

The aim is to make the behavior of a reinforcement-learning policy, and its consequences within the simulation, observable, reproducible and open to scrutiny.

**This is a research and educational prototype, not a clinical decision-support tool.** Its outputs are generated by a simplified simulation. They are not clinical treatment recommendations, evidence of antibiotic efficacy, or proof that a strategy will prevent antimicrobial resistance in real-world settings.

## Problem and research question

Antibiotic selection is a sequential problem: each choice can change the resistance profile and therefore the antibiotics that remain susceptible later. This project studies that problem in a controlled simulation rather than in patients.

> How does a frozen PPO policy compare with a random susceptible-action baseline in a simulated antibiotic-sequencing environment, in terms of resistance burden, resistance emergence, and the preservation of susceptible options?

The question is specific enough to evaluate and does not presuppose the answer. The project does not claim that PPO is superior, optimal, or capable of preventing AMR.

## Scope and intended use

* **For:** researchers, students, and others exploring reinforcement learning for antimicrobial-stewardship research.
* **Not for:** patient-specific prescribing, diagnosis, or any clinical decision. The system is not clinically validated and handles no patient data.
* **Terminology:** this document and the user interface use "PPO-selected action", "simulated outcome" and "susceptible-action rate", never "best antibiotic" or "effective treatment".

## How the simulation and the PPO policy work

* **State:** binary resistance (susceptible or resistant) to seven antibiotics: ciprofloxacin, nitrofurantoin, fosfomycin, trimethoprim, gentamicin, mecillinam and ceftazidime, giving 128 possible profiles ([action-space.md](docs/scientific-specification/action-space.md), [data/processed/action_space.csv](data/processed/action_space.csv)).
* **Episode:** at each of up to eight steps, a policy selects one antibiotic. An episode ends at the horizon, or earlier when every antibiotic is resistant and no feasible action remains.
* **Action mask:** only antibiotics that are susceptible in the current simulated state are feasible (`susceptible_actions_only`).
* **Transitions:** after an action the simulator samples one modeled outcome from the candidate transitions for that action in that state: cross-resistance, collateral sensitivity, or neutral. The candidate data come from [data/processed](data/processed) and the evidence registry. See [resistance-transition-model.md](docs/scientific-specification/resistance-transition-model.md).
* **Reward:** the negative normalized resistance burden ([reward-function.md](docs/scientific-specification/reward-function.md)).
* **Policies compared:** the frozen MaskablePPO checkpoint named in [ml/frozen_ppo_manifest.json](ml/frozen_ppo_manifest.json), and a baseline that samples uniformly among susceptible actions. The scientific code and specification call the baseline the *Greedy* policy; the public API labels it **Random Susceptible Baseline**. It is not an exhaustive or optimal search of antibiotic sequences.

Three distinctions are kept explicit throughout the project:

1. **Action selection:** what the policy chooses under the simulator's current action mask.
2. **Transition support:** whether candidate transition data exist for the selected action in the current state. A susceptible action can have none (`unsupported_no_candidate`); the simulator then leaves the profile unchanged. That is a data gap, not evidence of successful treatment.
3. **Simulated outcome:** how the resistance profile changes, or does not change, according to the environment. A lower simulated resistance burden is evidence about the modeled environment, not about clinical outcomes.

## System architecture

```text
React dashboard (planned) --> ASP.NET Core public API --> internal Python service --> frozen PPO checkpoint + simulator
                                       |
                                       +--> PostgreSQL (completed runs)
```

The browser talks only to the public .NET API. The Python service is internal and stateless, and PostgreSQL stores completed simulation and comparison runs. The API contains no scientific logic. See [backend/README.md](backend/README.md), [service/README.md](service/README.md) and [backend/docs/api-contract.md](backend/docs/api-contract.md).

## Key features

* **Profile exploration:** validate any of the 128 starting profiles and see which actions are feasible.
* **Trajectory comparison:** run the PPO policy and the baseline from the same starting profile and inspect step-by-step resistance trajectories (single stochastic runs, with their seeds recorded).
* **PPO action inspection:** view the PPO-selected action at each step with its transition-support status.
* **Run history:** completed runs are persisted and retrievable.

The API and persistence for these features are implemented. The dashboard that presents them is planned.

## Metrics

Every API response carries the definition of each metric it reports (`metricDefinitions`), taken verbatim from the scientific service. All values describe one simulated episode; none is a clinical outcome.

| Metric | What it measures |
|---|---|
| Cumulative resistance burden | Negated cumulative reward: the sum over steps of resistant antibiotics after the step divided by 7, with an all-resistant state charged for the remaining horizon. Lower means less simulated burden. |
| Resistance-emergence events | Number of steps after which the resistant count increased. |
| Final susceptible count and change in susceptible count | Antibiotics still susceptible at the end of the episode, and the difference from the start. |
| Susceptible-action rate | Share of steps whose selected antibiotic was susceptible in the simulator. The action mask makes this 1.0 for both strategies; it is not clinical effectiveness. |
| Unsupported step count | Steps where the selected action had no candidate transition. |

The full list, units and aggregation rules are in [backend/docs/api-contract.md](backend/docs/api-contract.md) and [evaluation-metrics.md](docs/scientific-specification/evaluation-metrics.md).

## Scientific assumptions and limitations

* A simplified model: binary resistance, seven antibiotics, a fixed eight-step horizon, and one transition-data scenario (`REF_UNIFORM_SUPPORTED`). The horizon is a computational parameter, not a treatment duration ([simulation-horizon.md](docs/scientific-specification/simulation-horizon.md)).
* The application serves one frozen checkpoint (`ppo_seed_12000`) out of the 20 trained seeds in [artifacts/ppo](artifacts/ppo). Conclusions about the policy in general require the multi-seed evaluation, not a single run.
* One comparison is a single stochastic sample. It does not show that either strategy is better.
* The same seed for both strategies does not guarantee identical transition outcomes, because candidate transitions depend on the selected action and state.
* Transition data are limited; actions without candidate data leave the state unchanged.
* Not clinically validated. No patient data are used or stored.
* The prototype API has no authentication, rate limiting, or CORS policy and is not intended for public deployment. See the "Known limitations for frontend integration" section of [backend/docs/api-contract.md](backend/docs/api-contract.md).

The full scientific specification is in [docs/scientific-specification](docs/scientific-specification).

## Testing and reproducibility

```powershell
python -m pytest
```

The suite covers the simulation core (state, actions, transitions, environment, reward), the PPO pipeline, the seed-study helpers and the internal Python service. The .NET unit, integration and live tests are described in [backend/README.md](backend/README.md). GitHub Actions (`.github/workflows/ci.yml`) runs the .NET tests, the Python tests and the live end-to-end tests.

Reproducibility safeguards:

* The service verifies the checkpoint SHA-256, the transition-data hash and the manifest contract at startup, and refuses to serve runs if any check fails.
* Checkpoints and study files are verified with `SHA256SUMS.txt` (see below).
* Every API run records the model identifier, checkpoint hash, seeds and metric definitions it used.

## Final PPO checkpoints

`artifacts/ppo/ppo_seed_<S>/` contains one folder for each of the 20 training seeds, from 1000 to 20000 in steps of 1000:

* `final_model.zip`: the MaskablePPO checkpoint. Its SHA-256 was checked against the research archive manifest.
* `config.json`, `environment_manifest.json`, `training_summary.json`: per-seed training provenance.
* `training_ledger.json`: run ledger for seeds 6000 to 20000. Seeds 1000 to 5000 have no ledger in the canonical study folder.

Shared files:

* `protocol_lock.json`: study protocol lock.
* `checkpoint_manifest.json`: per-checkpoint source paths, SHA-256 hashes, sizes, and archive match status.
* `SHA256SUMS.txt`: hashes for every file under `artifacts/ppo/` except itself. Binary files (`final_model.zip`) are hashed as raw bytes. Text files (`.json`, `.txt`, `.csv`, `.md`) are hashed after CRLF to LF normalization, so the same hash holds for Windows (CRLF) and Linux (LF) checkouts.

Per-episode training logs (`training_episodes.json`) are not included in this repository.
To verify a checkpoint, compute its hash and compare it with `checkpoint_manifest.json`:

```powershell
Get-FileHash -Algorithm SHA256 artifacts\ppo\ppo_seed_1000\final_model.zip
```

Load a checkpoint in Python with `load_ppo_model` from [ml/src/ppo_training.py](ml/src/ppo_training.py).

To verify every file against `SHA256SUMS.txt` under that policy, from the repository root (exit code 0 means all verified):

```powershell
.\.venv\Scripts\python.exe -m ml.src.artifact_checksums
```

On a Linux checkout, `cd artifacts/ppo && sha256sum -c SHA256SUMS.txt` gives the same result because the files are already LF. The hashes embedded in `checkpoint_manifest.json` for `protocol_lock.json` and the per-seed provenance files are not covered by this policy and were left unchanged.

## Study commands

The study tooling in [ml/src/ppo_seed_study.py](ml/src/ppo_seed_study.py) operates on the canonical study root by default. Its subcommands are `train`, `quarantine`, `verify`, `evaluate`, `report`, and `quarantine-evaluation`. Exit codes are 0 for success, 1 for an incomplete verification, 2 for a refused action, and 3 for a failed run.

`verify` writes `manifest.json` into the study root, so run it only against a complete canonical study. The runbook is in [docs/scientific-specification/ppo-seed-study-runbook.md](docs/scientific-specification/ppo-seed-study-runbook.md).
